# A supporter grant that ends by itself

## What

Ported from the downloader repo (its commit 8785bf6). `pnpm pro <email> --until YYYY-MM-DD|1y`
stores an end date and Pro switches itself off then; plain `pnpm pro <email>` is lifetime and
clears any date; `--revoke` clears both.

- `migrations/0015_pro_until.sql`: `users.pro_until`, `supporters.ends_at`, nullable epoch ms, null = forever.
- `isEntitled` honours `pro_until` for the `pro` grant only (`grantedProAt`); subscriptions are untouched.
- `claimSupporterGrants` copies `ends_at` onto the account at sign-in.
- `scripts/pro-until.mjs` parses the flag and throws on a typo.
- Every place that reads `users.grants` for an access decision now selects `pro_until` too: session
  columns, community directory, public list, public profile, the push-alert query, the plan card's `granted`.

## Mistakes

Copying the downloader's diff would have missed Reely's extra readers: grants are read in four SELECTs
and a raw `LIKE '%pro%'` in the push sweep. A dated grant that lapsed would still have received alerts,
a public profile and the plan card's "granted" flag. Found by grepping every `grants` reader, not by the diff.

## What worked

Tests red first (exact-end-second, claim carries/clears `ends_at`), parser throws on every bad input.
Sharing one `grantedProAt` so the plan card and `isEntitled` cannot drift.

## Rules

- A new column on an entitlement row must be added to every SELECT that feeds `isEntitled`; grep `grants` first.
- A flag that grants or ends access throws on bad input rather than defaulting.
